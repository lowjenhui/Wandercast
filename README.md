# Wandercast

*Your wanderlust forecast.* A playful, storybook-sky look: pastel skies, cream cards, rounded Fredoka headings and Nunito body text, with **Puff**, a little cloud mascot (`src/components/Brand.tsx`), in empty and loading states. Map rating colours and charts keep their plain, data-first palette. Light and "storybook night" dark themes are both included.

Checks whether a trip from Singapore (SIN) to a destination, for given dates, usually has pleasant weather and whether the fare is good value. Everything comes from historical evidence: no accounts, no saved trips, no preferences.

## Run

```bash
npm install
cp .env.example .env.local   # add your free Travelpayouts token and SerpApi key (both optional)
npm run dev
```

Without a token, the weather assessment works fully and the Flights section shows fares saved earlier, or says no airfare provider is configured if there are none. No fares are ever invented.

## Weather database

`npm run dev` / `npm run preview` also run a small local cache server (`server/`, mounted as a Vite plugin) that stores Open-Meteo data in SQLite at `data/weather.db`. It uses Node's built-in `node:sqlite`, so it needs Node 22.5 or later. The browser calls `/api/om/{archive,forecast,air-quality}` with Open-Meteo's own parameters:

| Data | Stored as | Freshness |
|---|---|---|
| ERA5 history | One row per place per day; overlapping ranges are only fetched once | Permanent (days within 10 days of today are re-checked) |
| 16-day forecast | One row per place per day, plus the 12 days before each fetch (same 2 units) | 6 hours; past days kept 35 days for recent rain |
| "Right now" map | 48 h of hourly weather and air quality per place, served from the DB only (the current hour while covered, otherwise the hour it was loaded); the map shows when it was loaded | Never refreshed automatically and not seeded. The API is called only when the user presses **Reload map**, and only for places loaded more than an hour ago (about 2 units per place) |
| Current air quality | Response per place | 30 min |

All upstream calls are metered with Open-Meteo's weighting (per location, per 14 days, per 10 variables). Limits: 500 units/min, 4,500/hour, 9,500/day. The day is split so no lane starves another: background work never touches the last **2,000** units (kept for your own searches), the **saved-dates lane** (saved destinations, requested places, saved date ranges) has its own **4,500**/day cap, and **general seeding** (full years, forecasts) its own **3,000**/day.

**How the app asks for weather** (built so one gap or a busy budget doesn't block what's stored):
- **Typical weather for suggestions, the "Your dates" map and saved-dates ideas is read from the database only** (`/api/om/archive?stored=1`). It makes no API calls while you browse. Places with fewer than 3 of 5 years stored (2 of 3 for long ranges) show "Not stored yet" and are added to a background queue (`wanted_era5`, `server/wanted.ts`). The seeder fetches them first on the saved-dates lane, and the app re-checks them (free) every 90 seconds for up to an hour. Places with 3 or 4 years stored are rated from those years.
- **Per-place results.** A multi-place request returns every stored place. A place the API couldn't fetch comes back `missing` with a reason, instead of the whole batch failing. Each window is handled separately in the browser too. Single-place requests (the full trip analysis) still return the error so they can retry.
- **Failures are isolated.** Each group of places is its own upstream request. One failing group doesn't stop the others, and identical fetches already in progress (e.g. the map and suggestions asking for the same place) are shared, not repeated.
- **Forecasts** (trips starting within 16 days) are still fetched live, since they change, and stored for 3 hours.
When the budget is busy, a live request gets `429` with `Retry-After`, and the app waits and retries.

**Background seeding** fills the database in priority order: (1) popular cities, meaning direct-flight cities with two or more airlines plus the curated destinations, (2) Southeast Asia, (3) the rest of Asia, (4) everywhere else. It first fetches 16-day forecasts for every place and keeps tiers 1–2 fresh. Then it fetches ERA5 history newest year first: the current year plus 5 years for all tiers, then 10 years for popular cities. Seeding uses at most 250 units/min and 3,000/day, never touches the last 2,000 daily units, keeps running when the saved-dates lane is capped for the day, and only runs when the app itself is idle. Requests within 10 km of a stored place reuse its data. Full history for every place takes several weeks within the free tier; popular cities' recent years are done within the first few days. Progress is shown under the map and at `/api/om/status`. Set `WEATHER_SEED=0` to turn seeding off.

**Copernicus import (optional):** `python3 scripts/import-era5-cds.py` fills ERA5 history from the Copernicus Climate Data Store's point time series instead, so it doesn't use the Open-Meteo allowance. It's the same ERA5 reanalysis, requested at the grid point Open-Meteo picked for each place, and converted to daily values with Open-Meteo's formulas in the place's local time. Two corrections make it match Open-Meteo: rain is moved back an hour, and temperatures get each place's height correction, measured from the days Open-Meteo already stored (Kuala Lumpur +1.6 °C). Checked over 10 years for 3 places: temperatures within 0.1 °C on average, rain within 0.25 mm/day. Rows are stored with `source = 'cds'`. No stored value is ever changed: on days Open-Meteo already stored, Copernicus only fills blank values (feels-like on days stored before the app saved it), and Open-Meteo only fills what Copernicus can't provide (snowfall). Missing snowfall never holds up a page: what's stored is shown straight away, and the blanks are queued for background download. It needs a free Copernicus account, `pip3 install cdsapi` and a key in `~/.cdsapirc` (setup steps at the top of the script). Run `--validate` first to compare a few places with the days Open-Meteo already stored. Tests: `python3 scripts/test_import_era5_cds.py`.

## Holidays & events

Also stored in `data/weather.db`, and served from `/api/cal/{holidays,events,china,trip}`:

- **Public holidays:** Google Calendar's public holiday calendars, which cover about 2021–2029 and mark public, regional and observance days, with Nager.Date as a fallback. Holidays are fetched per country on first use and refreshed every 30 days. The server pre-loads China and Singapore first, then countries in seed-priority order.
- **China break periods:** consecutive public-holiday days plus adjacent weekends (e.g. National Day Golden Week, 1–7 Oct). Years after 2026 are marked provisional until the State Council publishes the official schedule, usually in November.
- **Crowd events** (`server/eventsData.ts`): 36 curated recurring events with crowd and price impact, e.g. Spring Scream (Kenting), Songkran, Loy Krathong / Yi Peng, Golden Week, Sapporo Snow Festival, Seollal, Chuseok, Nyepi (Bali shutdown), Lebaran, Tết, Sinulog, Diwali, Oktoberfest and the Melbourne Cup. Dates come from rules: fixed dates, linked to a public holiday, nth weekday, lunar full moon (±1 day), or typical timing. Each is labelled accordingly and linked to a source. They are expanded into dated rows for the surrounding years.
- **In the app:** the home page warns when your dates overlap a China public holiday. Choosing a destination shows that country's holidays and events for your dates. The trip analysis adds a "Holidays & events" section: events on your weekends, long-weekend breaks, distance from your destination, China and Singapore (departure-side) breaks, and crowd and price alerts that also appear in the summary.

The Travelpayouts token is used by the local fare cache (`server/fareCache.ts`, `/api/fares/*`), so it never reaches the browser. Every fare response is saved in SQLite (`fare_cache`). A save from the last 6 hours is served without calling the API. When the API fails (rate limit, rejected or missing token, network), the last save is served instead and the Flights section says **Showing saved fares** with the save time. Fares for upcoming saved-dates destinations are also pre-fetched in the background (`server/farePrefetch.ts`, one request every 20 s, refreshed every 6 hours). Departures that have passed are hidden and pruned. Status: `/api/fares/status`.

**Live fares (optional):** with `SERPAPI_KEY` set, each full trip analysis also asks Google Flights (through SerpApi, `server/serpapi.ts`, `/api/live-fares/*`) for one-way prices: out on the start date, and back on the evening before and on the end date (the end date is the day you land in Singapore), so 3 searches per trip. City codes are expanded to their airports (TYO → HND, NRT). Results go through the same fare cache: reused for 6 hours, served as **Showing saved live prices** when SerpApi can't be used, and dropped once the departure passes. Successful searches are counted per month (`fare_usage`), re-synced from SerpApi's free account endpoint at startup and every 30 minutes, and stop at `SERPAPI_MONTHLY_LIMIT` (default 250). Saved-dates destinations get one background set of searches each, and background searches stop with 40% of the month's allowance left. The cheapest outbound plus return becomes the fare the value verdict judges (unless you enter your own). Status: `/api/live-fares/status`. For a static production host, you'd need a small server or serverless function that does the same.

**Flight rules** (`src/lib/flightRules.ts`, editable under **Flight rules** in the Flights section, stored at `/api/settings/flight-rules`) rank the live options for a working traveller. Workdays are Mon–Fri except Singapore public holidays. Outbound on a workday: leave 18:00 or later (**After work**); otherwise land 06:00–09:00 (**Early arrival**). Return landing on a workday: land by 06:00 (**Back before work**); otherwise leave 22:00 or later (**After dinner**). Connections need layovers of 60 min–2.5 h, not overnight, at the same airport, and at most 3 h longer than the fastest flight. Trips of 4 days or fewer show a connection only if it's 20% cheaper than non-stop, and a short connection to Japan priced at or below non-stop ranks with non-stop. Within each group, more hours at the destination (in 2-hour steps) comes first, then price. **Avoid connections through the Middle East** (on by default, a switch above the flight tables) leaves out connections in the UAE, Qatar, Bahrain, Kuwait, Oman, Saudi Arabia, Jordan, Israel, Lebanon, Iran, Iraq, Syria and Yemen (Turkey and Egypt aren't included; the route a non-stop flies over can't be checked). **Long-haul** routes (fastest flight 10 h or more, e.g. London) get a fourth, round-trip search. Non-stop ranks first unless its return ticket costs 40% or S$400 more (whichever is less) than the cheapest acceptable connection; then it stays listed but after the connections, with the difference shown. Connections Google lists among its best flights are kept whatever their layovers (**Google pick**). Workday returns can't land by 06:00 from that far, so they're ranked by the latest departure landing on the end date. Red-eyes (in the air 01:00–05:00, departure-city time) get a 🌙 flag. Airline logos come from Google Flights, with the airline code shown if a logo doesn't load. Cached fares ±1 day that are 15% and S$50 cheaper are suggested with an **Analyse these dates** link. Each flight shows typical carry-on and checked-bag allowances for its airline (`src/data/airlineBaggage.ts`: included allowance, or a pre-booked 20 kg fee each way), as labels that aren't added to the price.

## Method

- **Workflow:** pick dates, then either enter a destination (*Evaluate trip*) or leave it blank (*Suggest destinations*). Choosing *Analyse* on a suggestion, or on a destination selected on the map, runs the full evaluation.
- **When to go (reverse search):** switch the search bar's dates to **Flexible** (a trip length instead of start and end dates) and choose **Find best dates**, or press **When to go** in a place's map popover, on the selected Sunny picks card, or beside the trip analysis title. Picking a window switches the bar back to **Fixed** with those dates. Every start date over the next 12 months is scored for a 2–30 day trip (`src/lib/bestTime.ts`): the same calendar dates in the last 10 archived years, slid ±3 days, weighted by recency (half-life 12 years) and, within 7 months, by ENSO phase, then rated with the same suitability score and seasonal-risk penalties as the trip analysis. An **Any days │ Weekends** switch scores only weekend trips instead (Sat–Sun 2D1N, Fri–Sun 3D2N or Fri–Mon 4D3N; 52 weekends on the strip, Singapore long weekends marked ★); it opens on weekends for places 3 hours or less away. Below the strip, cards reuse the trip analysis for the whole year: Safety & insurance (as if booking today), Through the year (monthly rainfall chart, wet days, highs and lows from the same history), Seasonal weather (curated risks with their months) and Crowds & celebrations (grouped by month). It shows the 3 best start dates (at least 14 days apart, with the chance of a mostly dry trip), a year strip coloured by rating, each month's best start, and the worst stretch as **Avoid** with its reason. When scores stay within 6 points all year it says so (e.g. "Good most of the year") instead of naming winners. Holidays and events (3+ day public-holiday breaks, China breaks, curated crowd events) are marked on the strip for trips that would overlap them, but don't change the score. History is read one calendar year at a time (about 11 years; stored years cost nothing, missing ones are fetched on the search lane, about 27 units each, and stored permanently). Clicking a window, a day on the strip or a month runs the full trip analysis for those dates.
- **Sunny windows layout:** the page follows the trip analysis and Puff's Lookout. A header card holds Puff (searching while history loads, then happy or sleepy by the best window's rating), the place, a subtitle with the next 12 months and the SGD rate, and one **Trip** row (Any days | Weekends) with **Length** (a stepper, or 2D1N / 3D2N / 4D3N chips for weekends). Below it come the summary row (**Weather outlook**: best months, best starts and the stretch to avoid; **Air quality**: the AQI right now from PM2.5 and PM10, until the air-quality layer adds typical months; **Safety & insurance** as if booking today), Recent alerts, **The best windows** (best 3, Avoid, the year strip and each month's best), **The weather story** (a headline, Through the year, Seasonal weather and El Niño / La Niña boxes, then Rain lately; "not a forecast" sits in its subtitle) and **Crowds & celebrations** for the 12 months (month rows in the analysis's style, then China holidays and Singapore long weekends). Holidays and events show even when the weather history can't load.
- **Through the year** (`src/components/ThroughTheYear.tsx`, on the trip analysis, Puff's Lookout and Sunny windows): average rain as bars with the figure on each and no axis, on the same grid as the table below, so each bar sits over its month. The rows are wet days, high, low, feels-like high, humidity, daylight, and sunrise · sunset (local times on the 15th, calculated). The trip's months are tinted. On a phone, the bars and table scroll together with the labels pinned. Feels-like comes from stored history only: months still missing it show "…" and are queued for the background download, which fetches every variable.
- **Rain lately** is the last section of The weather story on all three pages. On the Lookout, once the story folds (within 16 days), it sits at the end of The weather forecast card instead.
- **Exchange rates:** the trip analysis title, the Lookout header (one line per currency) and the Sunny windows subtitle show the SGD rate as plain text, e.g. "S$1 = ฿26.3 today", flipped to a round local amount when S$1 buys over 100 units ("¥1,000 = S$8.08"). `server/fx.ts` fetches ExchangeRate-API's open SGD endpoint at most every 12 hours (one request covers every currency), stores it in SQLite, and serves `/api/fx?cc=TH,JP`. Country → currency comes from world-countries; Singapore shows nothing. Attribution is in the footer.
- **Compare destinations for saved dates:** select a saved range to see **Destinations to compare**. Add places with the search box (known destinations come first, with fare codes and direct-flight info). Each row shows the weather rating, the chance of a dry trip, likely rainfall (middle half of past trips), the average high, flight or ferry time, and a ● flag for crowd or price alerts (events, holiday breaks, China and Singapore peaks). Click a row for the full analysis on those dates. Destinations are stored in SQLite (`saved_destinations`, `/api/saved/:id/destinations`). The server prefetches each one's full analysis history (`server/destPrefetch.ts`, using the same plan as the analysis, `src/lib/tripFetchPlan.ts`, about 300 units the first time) on the saved-dates budget lane, newest first and ahead of the map-wide prefetch. A row analyses once 95% is stored; the last few days come through the normal search budget.
- **Ideas by trip length:** under the comparison, the top 5 places for the range's typical weather that fit the **flight-time guide** (Balanced: day trip ≤1.5h, 2D1N ≤3h, 3D2N ≤5h, 4–5 days ≤6h, 6–9 days ≤8h, 10–14 days ≤13h, 15+ any; one-way direct flight estimated from distance; ferries always fit). **Exceptions** let favourite places through from a minimum trip length (default: Japan from 3D2N). They're editable under "Flight-time guide and exceptions" and stored in SQLite (`/api/settings/travel`). Ideas use the typical-weather data already saved for the range, so they cost no API budget.
- **Climate zones (ratings map):** Sri Lanka, Malaysia, Thailand, Vietnam, the Philippines, Taiwan, Australia, Indonesia, India, China and Japan are coloured zone by zone instead of by the capital, on both Right now and Your dates, each zone rated at its own city with the same scoring (so Sri Lanka's east shows Pleasant in July while Colombo has the southwest monsoon). Zones are clipped to the country outline being drawn; a faint dotted line marks where two zones meet (Map key: Climate zones). A zone whose city isn't stored yet shows as no data, never the capital's colour. The popover names the zone and its city, gives the city's details (with Analyse and Sunny windows), the monsoon seasons under way and where they rain, then every zone of the country with its rating (click one to switch). Legend counts and the country tables count each zone separately. Zone cities are seeded and prefetched with the popular places.
- **Map types:** a **☀ Weather ratings / 🌧 Rainfall & monsoons** switch on the right of the map header. Weather ratings has the **Right now** and **Your dates** tabs. Rainfall & monsoons (blue accent) has **Your travel months** and **Month by month**. Each type remembers its tab.
- **Map popover safety:** places with an MFA advisory or incomplete FWD cover start with a safety block: the MFA and FWD chips, MFA's reason in one line (the "In view of… / Due to…" clause of its guidance, with the page date and "Read MFA advice ↗") and FWD's rule in one line. Countries whose advice covers only some regions show "FWD: varies by area". Weather sources fold into "Sources (n)".
- **Map popover:** hovering shows a quick preview; clicking pins a popover anchored to the place (it follows pans and zooms, flips to stay inside the map, and docks under the map when the map is narrower than 600 px). For a destination it offers **Analyse** for the map's dates and **When to go**. Close it with ✕, Esc or a click on empty map. In rainfall mode any spot can be pinned.
- **Month by month (rainfall):** a smooth heat map of average monthly rainfall (mm/month), with a month slider, a play button that steps through the year, and labels for the monsoons and rainy seasons typically active that month, and dashed footprints where a monsoon mainly rains (Sri Lanka's southwest, northeast and two inter-monsoons, the Andaman and Gulf coasts of Thailand, peninsular Malaysia's east coast, central Vietnam, the Philippines' habagat and amihan sides, Taiwan's northeast monsoon and southern wet season, northern Sumatra and Maluku against Java and Bali, Australia's tropical wet season, east-coast storms and southern winter rains, India's two monsoons, and China's plum rains, southern pre-summer rains, northern rainy season, Yunnan, Hainan and Tibetan plateau wet seasons, Japan's Sea of Japan winter snow and Okinawa's earlier rainy season), bolder while it is active and highlighted when its label is hovered. It opens on your travel month. Your travel months are highlighted on the slider. Hovering anywhere shows that area's rainfall for all 12 months, its yearly total, and its wettest and driest months; click to keep the panel open. Zoomed in, the raster covers just the view and uses the 0.25° ERA5 grid over Asia and Australia (blended into GPCP over its last 3°), so neighbouring coasts show apart. In a country with climate zones, the pinned panel adds **Two rainy sides** (**Rain by area** with more than two zones): a 12-month strip per zone at its city with your months outlined and which side is drier then (or wet everywhere). The pinned panel also shows **Rain around here** anywhere: 12-month strips for up to 8 places within about 350 km (destinations first, then map cities), your months outlined, and the driest of them then (e.g. Abashiri against Hakodate in July). These are climate normals (about 275 km areas worldwide, 28 km over Asia and Australia when zoomed in), not a forecast.
- **Your travel months (rainfall):** the same heat map for your travel month(s), weighted by the number of trip days in each month.
- **Travel-dates outlook (map + suggestions):** if the trip starts within 16 days, it uses the Open-Meteo daily forecast for the covered days. Otherwise it shows typical weather for the same calendar dates over the last 5 years of ERA5 history, labelled as typical rather than a forecast. Years are weighted by recency and by El Niño / La Niña phase (see below). The windows stay on the exact dates, so the stored saved-dates history is reused without new API calls. Ratings use the same suitability score as the trip analysis. One very poor factor caps the rating, so dry but cold weather is not "Pleasant". Cool weather (average highs below 15 °C) is Generally pleasant at best, since humidity scores full marks when it's cool and would otherwise lift a dry, chilly trip to Pleasant (Beijing in March, Chengdu in January). Severe cold or heat (average highs at or below 0 °C, or at or above 38 °C) rates Challenging at best, however dry: Harbin, Mongolia and Kazakhstan in midwinter, the Gulf and the Sahel in summer, Delhi and Agra in May.
- **Trip odds (full analysis):** instead of one average, the analysis builds sample trips. For each of up to 25 past years, your trip is slid up to ±7 days around the same calendar dates, giving about 375 plausible trips. Each is weighted by recency (weight halves every 12 years), by closeness to your exact dates, and by ENSO phase. The panel shows the chance of a dry trip (at least 80% of days dry, e.g. 4 of 5), rain on most days, at least one downpour (≥20 mm), and at least one hot day (≥33 °C), plus the likely (middle-half) range of wet days and rainfall. The suitability score uses these weighted figures. The last 10 years come from the usual full-year fetch. Older years are fetched as small ±7-day windows (about 2 units each) and stored in `era5_daily`, so a repeat search costs nothing. If the API budget is busy, older years are skipped for that search (waiting at most 20 s) and the panel says so.
- **El Niño / La Niña:** the latest ONI season gives the current phase (±0.5 °C thresholds). For a future trip it is assumed to persist: at full strength up to 4 months ahead, at half strength 5–7 months ahead, and not at all beyond that. Past years in the same phase count 3×, opposite-phase years 0.3×, and others 1×. The panel also checks this place's own record: if at least 3 past years were in the expected phase, it says whether they were wetter, drier or similar at these dates.
- **Suggestions:** about 80 curated destinations (`public/destinations.json`, `npm run destinations`), ranked by weather score minus 3 points per estimated flight hour beyond two hours, or by weather only, or by flight time. Flight time is a direct-flight estimate from great-circle distance (800 km/h plus 30 min). Filter by maximum flight time. The list starts with the top 5 (**Show 5 more** adds more). Selecting a card, or the place on the map, expands it with **Analyse** and **When to go**; a place picked on the map that's ranked lower is pinned first with its rank, above ranks 1–4, so the list stays at five cards. Selecting a place on the map pans it to the centre so its popover fits. On the trip analysis, Sunny windows and Weather library pages, a sticky bar under the search bar keeps **← Back** and what you're viewing in reach.

- **Travel advisories & insurance:** Singapore MFA advice has no numbered levels, so the level comes from its wording: *defer all travel* ("defer/avoid all travel", "not to travel", "avoid travel to"), *defer non-essential travel*, or *exercise caution* (any travel notice). An advisory whose wording matches none of these shows **Check MFA**; it is never guessed. Each page's zones (whole country, Natural Earth states/provinces, a band along a border, or a circle) are curated in `src/data/advisoryZones.json` for MFA's current page date. When MFA updates a page, the whole country is flagged at the page's level until the zones are reviewed, and the server logs it. "Border regions" are read as 50 km bands and marked as approximate. **FWD:** excluded countries and regions are never covered. *Defer all travel* is not covered. *Defer non-essential travel* is shown as **likely not covered, confirm with FWD** (FWD excludes places where MFA "recommends postponing" travel). Caution notices don't affect cover. FWD covers advisories issued after you booked: with an optional **booked on** date (search bar or saved travel dates), the app says *not covered* when MFA's page predates the booking. It says *covered* only when its own history saw no advisory after the booking date; otherwise *covered only if issued after booking*. **Where it shows:** a **Safety & insurance** card beside Weather suitability and Airfare value (the Overall verdict is *Unfavourable* for *defer all travel*); hatching and border bands on the weather map (the **Advisories** pill, on by default); a line in map popovers; and Sunny picks and saved-date ideas, which leave out *defer all travel* places (listed under the picks) and flag the rest. Not insurance advice: the insurer's policy wording decides.
- **Recent unrest & security alerts:** other governments' alerts from the last 14 days (`src/lib/alerts.ts`), kept apart from MFA advice. US embassy Demonstration, Security, Weather, Natural disaster and Health alerts are kept; routine messages and the worldwide caution are skipped. Alert titles name the embassy, not the event, so the cities come from the alert's **Location:** line, or else from its event text, where a city counts only after a place word ("in Paris", "parts of Paris", "including Lille"). An embassy's own name ("U.S. Embassy Paris") is ignored, and a "countrywide" location names no city. UK FCDO updates are kept only when their change note is about unrest or security (protests, curfews, terrorism…), and are country-level. An alert belongs to a place when a city it names is within 50 km; alerts re-issued with the same text show once. **Where it shows:** a slim **Recent alerts** strip under the summary row of the trip analysis and Puff's Lookout, and above the cards on Sunny windows (city alerts ⚠, country-level ℹ, with source, age and link; only when there are alerts, otherwise the Safety & insurance card says there are none); a **Recent alert** chip in map popovers and on Sunny picks cards, for city-matched alerts only; and Puff's Lookout, which logs each new alert for a stop as a **New** item (the first check is the baseline). None of this changes MFA's level, insurance cover, the weather rating, or what lists leave out.
- **How it feels (full analysis):** feels-like (apparent) highs and lows, nights and cold, and daylight, with plain-language packing and planning notes (`src/lib/comfort.ts`). Feels-like temperature and snowfall (`apparent_temperature_max/min`, `snowfall_sum`) are read for your exact dates in each of the last 10 years only, about 1 unit per year the first time and stored afterwards (the `atmax`, `atmin` and `snow` columns). Every ERA5 and forecast fetch now asks for them too, at no extra cost (7 variables are metered like 4). Days stored before they were added are refetched only when a request asks for them. It shows the feels-like high vs the actual high, days that feel ≥38 °C or below freezing, the night low and coldest night, frost (<0 °C), cold (<5 °C) or cool (<15 °C) nights, and snow days (≥1 cm) with how many years had snow. Daylight is calculated from latitude and date (sunrise equation), so it needs no data: day length, local sunrise and sunset (DST-aware), and the difference from Singapore. These figures are shown alongside the suitability score and don't change it. Saved-dates compare rows skip them.

- **Recent rain vs normal:** rain over the last 7 and 30 days compared with the same days in the past 10 years of ERA5, from stored data only (`server/recentRain.ts`, `/api/recent-rain`). Recent days use ERA5 once settled and the past days stored with each forecast before that. **Wetter than usual** is ≥1.5× normal over 30 days or ≥2× over 7 days (with at least 30 mm); **Much wetter** is ≥2× or ≥3×. Places with under 30 mm of normal rain in 30 days are never flagged. The Right now map rings flagged places in blue (thicker for Much wetter) and the popover gives the last 30 days against normal. A **Rain lately** card (7-day, 30-day and wet-day tiles, 12 weeks of weekly rain against normal) shows on the trip analysis and Puff's Lookout from 30 days before a trip until it ends. It signals heavy rain, not flooding: floods from rivers upstream can show only moderately (Bangkok, Oct 2026: 1.6×).
- **Rainfall around the trip (full analysis):** a centred window of at least 30 days, padded equally before and after (at least 3 days each side), from the same 10 years of ERA5. It shows the daily wet-day chance and average rainfall, the before / during / after wet-day share, and, if one exists, a trip-length stretch with at least 10 percentage points fewer wet days.
- **Saved travel dates (compact):** a single row of chips (label, dates, weather-saved status). Selecting a chip shows its details and actions (View on map, Edit, Delete); **+ Add dates** opens the editor. Ranges of up to 92 days are stored in SQLite (`saved_ranges`; `/api/saved` supports GET, POST, PATCH and DELETE). Add, edit and delete them in the "Saved travel dates" panel, which has its own label and date fields, prefilled from the search dates. Duplicate ranges are rejected. **View on map** fills in the search form's dates and switches the weather map to that range. Editing the range in use keeps the form and map in step. **Weather for saved dates is pre-fetched:** for every map destination and country capital (436 places, popular → Southeast Asia → Asia → rest), the seeder stores the same-date ERA5 history the map and suggestions use (5 years, or 3 for ranges over a month), plus the forecast when the range starts within 16 days. This runs on the saved-dates lane (4,500 units/day, after saved destinations and requested places), alongside general seeding's own share. Each saved range shows its progress, and "Retrieve these first" moves a range to the front of the queue (`POST /api/saved/:id/fetch`). Editing a range only fetches the days that changed. Ranges longer than a month use 3 years of typical weather instead of 5, to stay within the API budget. Trip analysis and suggestions still need 60 days or fewer.
- **Booked trips: Puff's Lookout.** Once tickets are bought, **✈ Mark as booked** on a Daydream date opens a two-step **Finalise**: (1) tick the places you're visiting, in order, with nights that add up to the dates (places left out are deleted from the range after their saved fares are copied into the trip archive; weather history is kept anyway), then (2) choose how you travel each leg: to and from Singapore only the ways the destination data knows (flight, ferry, coach, bus, train, shuttle van), between stops any way. **✈ I've booked this** on a trip analysis books that one place (saving the dates and place under Daydream dates if needed) and goes straight to step 2. The trip moves to an **On Puff's lookout** strip above Daydream dates (route and first leg's icon, countdown, a dot for unread changes). Booking stops fare prefetch, map-wide weather prefetch and ideas for that range, and freezes each stop's analysis summary as a baseline. **Change plans** moves it back to Daydream dates. Puff's Lookout is the only page for a booked trip (analysing it from search links to the Lookout instead): a white header card with a sky band, Puff (binoculars, the only Puff on the page), the trip, countdown and Change plans, then two columns (stacked on narrow screens): **What Puff spotted** (changes since booking and since your last visit, marked **New** and named after the stop when there are several, plus "since booking" comparisons; when all is quiet, **Coming up on the lookout**: when the daily forecast, air quality and weekly events checks start, and daily MFA advice) beside **Your trip** (one line per flight, drive or stay in trip order, with operator or flights, times, stay names and prices once added, a trip total and the booking date; Edit or **+ Add times, stays and prices** opens the editor across the card); the summary cards (Weather outlook, Air quality, Safety & insurance with the strictest advice across stops); **The weather forecast** (once within 16 days: a tile per trip day tagged with where you'll be, a travel day counting for the place you arrive at; compared with typical; packing notes); **The weather story** from the trip analysis per stop (tabs), folded under the forecast once it's in range; **Air quality** (5-day CAMS forecast, US AQI from PM2.5 and PM10 as aqicn.org headlines, PSI ≈ hint, live reading during the trip); **Crowds & celebrations** from the analysis per stop, with Google Events via SerpApi; and **Getting there** (each leg with ferry or overland route details, causeway alerts and Singapore holidays). Nearby GDACS cyclones and fires show under the summary. The server watcher (`server/lookout.ts`) checks each stop over its own dates every 10 minutes: forecast and air quality every 3 hours once in range (saved-dates budget lane), Google Events weekly from the month before (the same 250-a-month SerpApi allowance as live fares, background searches keep 40% back), and each country's MFA page daily. The first check is the baseline; later differences (rain chance ±20 points, highs ±3 °C, an AQI band change, new events, an MFA level or page change) are logged in `lookout_changes`. Routes: `POST /api/saved/:id/book` (`{ itinerary, booked_on, baseline?, prune? }`, also used to edit), `DELETE /api/saved/:id/book`, `GET /api/saved/:id/lookout`, `POST /api/saved/:id/lookout/seen`.
- **Map cities:** every city with a direct flight from Singapore is drawn with a bold outline at every zoom level. Overlapping ones thin out when zoomed out and separate as you zoom in. Other cities appear as you zoom in.
- **Map outlines (level of detail):** Natural Earth 110m for the world view, 50m from regional zoom (adds islands such as Batam, Bintan, Karimun and Langkawi), and 10m coastlines close up. The detailed sets load lazily (about 240 KB and 1 MB compressed). When zoomed in, only countries in view are drawn. Polygons wound the wrong way in the source data (e.g. the Maldives at 10m) are corrected on load.
- **Desktop planner (wider than 1,100 px):** the side column and the map column each fill the window below the search bar and scroll on their own, with thin scrollbars and a fade when there's more below. The disclaimer footer is at the end of the map column. Narrower windows stack and scroll as one page.
- **Map view:** opens centred on Singapore and Southeast Asia. Pinch, double-click or ⌘/Ctrl + scroll to zoom (plain scrolling scrolls the page or pane, with a one-time hint), drag to pan; SG and World buttons switch views. Cities appear as you zoom in (with a ×4 population weight inside SE Asia), decluttered to keep at least 16 px between dots.
- **Phenomena:** *Now* entries come from live data: thunderstorms, heavy rain, haze (PM2.5 ≥ 35.5 µg/m³; labelled "smoke haze" when a GDACS fire is within 500 km), dust, fog, tropical cyclones within 800 km, extreme heat or cold, and gales. *Season* entries are typical regimes for the current month from the curated reference, e.g. the Andaman Sea southwest monsoon, Singapore's inter-monsoon and monsoon phases, and transboundary haze.
- **Current weather map (home page):** *Bad* means a thunderstorm, heavy rain or snow, a feels-like temperature ≥ 38 °C or ≤ 0 °C, or wind ≥ 50 km/h, unhealthy haze (PM2.5 ≥ 55.5 µg/m³) or a tropical cyclone within 300 km. *Average* means light rain or drizzle, fog, a hot (> 31 °C) or cold (< 12 °C) feel, wind ≥ 30 km/h, or muggy air (≥ 85% humidity at ≥ 25 °C), hazy air (PM2.5 ≥ 35.5) or other elevated pollution (US AQI > 150). *Good* means none of these. Countries too small for the 110m outlines are drawn as dots.

- **Historical windows:** the same calendar dates in each of the 10 most recent years whose window ended at least 7 days ago (ERA5 publishes with a delay). Last year means the most recent such window.
- **Wet day:** a day with ≥ 1 mm of precipitation. A heavy-rain day has ≥ 20 mm.
- **Suitability score:** rain 45%, temperature 35%, humidity 20%, minus penalties for overlapping high or moderate seasonal risks. Confidence drops with fewer years or very variable rainfall.
- **Fare benchmark:** return fares departing within ±21 days with a similar stay (±30% of nights, min ±2). A median or range is shown only with at least 8 observations. The value verdict compares your manual fare (or the cheapest cached exact-date fare) with the quartiles. The seasonal position compares the comparable-trip median with the route-wide median.
- **Overall conclusion:** given only when both weather and fare evidence are sufficient.
